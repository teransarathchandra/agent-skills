# Role profile: technical writing

Load this when the person writes documentation: product docs, API docs, developer docs, content design. Follow it for intake, evidence, CV shape, keywords and screening answers.

## Titles and adjacent roles

- Common titles: Technical Writer, API Documentation Writer, Documentation Engineer, Content Designer, Information Developer, Developer Advocate (docs-focused), Knowledge Base Manager.
- Realistic moves after a layoff: writer to docs engineer or developer educator; support or QA to technical writer; writer to content designer or UX writer.
- Search the person's title plus "documentation" and "content".

## Evidence sources

- Published docs: public help sites, API references, release notes, tutorials with links and dates.
- Docs repos: Markdown, reStructuredText or AsciiDoc in Git; the person's own commits and pull requests.
- Outcome records: support ticket drops, search or page metrics, time to first call for an API, doc coverage, review turnaround.
- Documents: style guides written, templates, migration plans, praise from engineers.
- Public: published articles, open-source doc contributions, a portfolio site. Private under an NDA: unreleased product docs, internal wikis, customer names. Rewrite a sample from public information instead.

## Intake questions

1. Which kind of writing is the strength? (answer as it is: API, user guides, developer docs, content design)
2. Which direction do you want?
   a) **Same role and level (Recommended: strongest evidence)**
   b) Toward docs engineering and docs-as-code
   c) Toward content design or UX writing
   d) Other: type it
3. Where is the proof of your work? (pick any)
   a) **Published links and a docs repo (Recommended: readers can check)**
   b) Metrics: ticket reduction, page views
   c) Documents: style guides, templates
   d) Other: type it
4. Which tools have you used for authoring and publishing? (answer as it is: Markdown, Git, Confluence, MadCap Flare)
5. Do you have a portfolio?
   a) **Yes, send the link (Recommended: most ads ask for samples)**
   b) No, help me pick three samples
   c) Other: type it

## CV shape

- Order: header, summary, skills (authoring, docs-as-code, API, tools), experience, portfolio link, education.
- Summary leads with years, the content type (API, developer, user), the audience and the publishing method.
- Bullets, action then result then how:
  - "Cut support tickets on setup by about a quarter by rewriting the onboarding guide and adding runnable examples at Example Logistics."
  - "Documented 60 REST endpoints from an OpenAPI spec, giving developers a searchable reference, using Markdown, Git and a static site generator."
  - "Set up a review workflow in GitHub that took doc updates from 5 days to 1 with CI link checks."
- Put the portfolio link in the header.

## Keywords and credentials

- Keywords from the ad: API documentation, OpenAPI, Swagger, REST, Markdown, Git, docs-as-code, static site generator, CI/CD, DITA, Confluence, style guide, Agile, SME interviews.
- Many ads for developer docs ask for Git, Markdown and OpenAPI familiarity and a sample portfolio. No certification is widely required. The Certified Professional Technical Communicator (CPTC) from the Society for Technical Communication (STC) exists in tiers (Foundation, Practitioner, Expert) but is rarely asked for in the ads sampled. Confirm any named credential in the target ads.

## Portfolio and work samples

- Commonly expected. Include two to four samples: one API or reference, one tutorial or guide, one that shows process (before and after, or a pull request).
- Use samples the person can publish: public product docs they authored, open-source work, or a rewrite of a public API. Make code samples run. Never publish employer-internal docs.

## Screening questions

- "Years of technical writing": count writing roles only.
- "Experience with API docs / OpenAPI": yes only if in the bank; give the number of endpoints if known.
- "Can you read code?": answer with the languages the person can read.
- "Writing sample required": send the portfolio link; if none, say samples will follow.

## Answer-bank experience keys

Collect lowercase keys with years or true/false: `markdown`, `git`, `openapi`, `swagger`, `rest apis`, `docs-as-code`, `static site generator`, `confluence`, `madcap flare`, `dita`, `asciidoc`, `figma`, `python`, `javascript`, `ci/cd`, `style guide`.

## Mistakes to avoid

- No samples, or samples full of lorem ipsum.
- Duties without audience or result ("wrote documentation").
- Sending confidential internal docs as a sample.
- Typos: a writer's CV is itself a sample.
